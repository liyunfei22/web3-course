# list-concurrency.md — Go 并发专项 15 题必做清单

> 定位：roadmap W19「Go 并发专项 15 题必做（交替打印/限流器/worker pool/生产者消费者/select 陷阱等）」，是算法轮并发题的题库，也是 `interview/go-deep-60.md` 的动手部分。
> 交付标准（每题）：①写出可编译可运行的完整程序 ②`go test -race` 全绿 ③能对着代码讲 60 秒「用了什么原语、为什么这样不会出问题」④至少过 1 个面试官式追问。
> 每题只给「题目语义 + 考察点 + 常见错误 + 验证方式」，不给完整答案——先自己写，卡 30 分钟再查资料（卡壳 30 分钟规则）。

## 题 1：交替打印数字和字母

- **题目**：两个 goroutine 轮流打印「1,2,3」与「A,B,C」，输出 1A2B3C 交替合并为 1A2B3C（或 12A34B 变体）；循环 N 轮。
- **考察点**：无缓冲 channel 的同步互斥语义（一次交接 = 一次握手）；goroutine 调度顺序不保证，必须靠 channel 而非休眠联动。
- **常见错误**：用 sleep 对齐节奏（慢环境顺序错乱）；双人各持一发一收导致自锁；只用一个 channel 的两个方向未配对导致 deadlock。
- **验证**：跑 10000 轮输出序列稳定；`go test -race` 无警告。

## 题 2：三个 goroutine 交替打印 ABC

- **题目**：三个 goroutine 循环打印 A、B、C，输出 ABCABC……共 N 组（循环依赖推进，链条式交接）。
- **考察点**：链式 channel 接力（A → B → C → A）；主 goroutine 如何等全部结束再退出（WaitGroup 或结束哨兵 channel）。
- **常见错误**：第三个 goroutine 忘「归还」回第一个，链条断；WaitGroup 位置写错导致提前退出/死等。
- **验证**：输出严格 ABC 循环；`-race` 干净。

## 题 3：生产者-消费者（有界）

- **题目**：M 个生产者、K 个消费者共享一个容量为 N 的队列（channel 实现），生产消费各自可暂停；统计总处理数。
- **考察点**：带缓冲 channel 的背压语义（backpressure）；关闭 channel 的「唯一关闭者」原则与 range 消费；用 close + WaitGroup 做铺排。
- **常见错误**：多个 goroutine 关闭同一 channel（panic: send on closed / close of closed）；消费者漏 range 导致数据丢失假象；生产者在「不空」时退出留下死锁。
- **验证**：总处理数 == 总生产数；关闭后无 goroutine 泄漏（runtime.NumGoroutine 前后一致）。

## 题 4：限流器（令牌桶）

- **题目**：实现令牌桶限流：桶容量 cap、补充速率 rate/s，请求来时取令牌，取不到则等待或拒绝；用于 API 网关按 IP 限流（P2 网关的简化模型）。
- **考察点**：带缓冲 channel 当令牌桶的直接实现；timer/Ticker 补币的精度与并发安全；「拒绝」与「等待」两种策略的接口设计。
- **常见错误**：补币用 for 循环 time.Sleep 各补一个（速率不准）；Ticker 开着不 Stop（资源泄漏）；桶容量与补币并发读写无锁。
- **验证**：请求并发压测下超速请求被限；`-race` 干净；讲清「这个实现假想生产里为什么用 Redis 而不是进程内」——回到 P2 网关。

## 题 5：worker pool 优雅退出

- **题目**：固定 N 个 worker 从任务 channel 取任务执行；收到「停止」信号后：不再取新任务、正在执行的跑完、全部退出后主函数返回（graceful shutdown 的 Go 版本）。
- **考察点**：close 通知 + range 消费模式；sync.WaitGroup 精确计数；context cancel 的二段式退出（软停止 vs 强杀）；顺序：「先关入口 → 再等 worker → 最后关资源」。
- **常见错误**：先 close channel 但 worker 还在取（正常）却有人在写（panic）；WaitGroup 与 close 顺序颠倒导致「等空」死锁；退出路径上对共享状态缺锁。
- **验证**：任意时刻 Ctrl+C 程序都能在几秒内干净退出；每轮退出时长与在途任务数吻合；-race 干净。

## 题 6：contains 超时（带超时的并发查询）

- **题目**：给定字符串数组与目标，并发把数组切片分给多个 goroutine 查找（contains），任一找到即整体返回 true；整体有时限，超时返回 false——模拟「扫块服务对批量地址的并发存在性检查」。
- **考察点**：context.WithTimeout 作为一等公民传递；select + context.Done 短路；「找到」传播（共享带锁结果或结果 channel + 非阻塞发送）。
- **常见错误**：超时后子 goroutine 仍在跑（泄漏，查 -race 与 NumGoroutine）；忘记「提前返回后其他 goroutine 怎么办」；用 time.Sleep 模拟超时而不测可真超时。
- **验证**：超时用例稳定在限时附近返回；子任务不泄漏；`-race` 干净。

## 题 7：并发安全 Map

- **题目**：实现一个并发安全的泛型 Map（Go 1.21+ 可用泛型）；要求：读多写少场景读写都支持，并给出「为什么不用原生 map」与「为什么这里不用 sync.Map」的论证（= 面试常问三选一：mutex 全锁 / RWLock / sync.Map）。
- **考察点**：mutex 与 RWLock 的取舍；sync.Map 的适用边界（写多/读多的 key 集稳定场景）；复制的 map 浅拷贝陷阱；读操作返回值的拷贝语义。
- **常见错误**：并发读写裸 map 直接 panic（fatal error: concurrent map read and map write）；锁粒度过大退化；返回内部引用让外部改「内部状态」。
- **验证**：-race 压测通过；与裸 map 对拍结果一致；能讲三种方案各自的 QPS 表现差异。

## 题 8：读写锁缓存

- **题目**：实现带过期时间的缓存：Get/Set，读多写少，用 sync.RWMutex；顺带解决「缓存击穿」——并发 Get 同一缺失 key 只允许一个 goroutine 去加载（singleflight 简版）。
- **考察点**：RWMutex 的读锁并行、写锁互斥；双重检查（double-checked locking）；singleflight 用 channel 合并并发请求——P0 短链服务缓存层的真实场景。
- **常见错误**：只加读锁覆盖写（写时读仍然看到旧值）；双重检查漏外检导致重复加载；过期时间判断与删除不加锁。
- **验证**：压测下读并发无 race；缺失 key 并发 Get 触发加载次数 == 1（日志计数验证）。

## 题 9：定时器任务

- **题目**：实现一个简单任务调度器：注册任务（间隔 + 函数），启动后按间隔执行；支持停止单个任务——模拟 P1 扫块轮询的调度骨架。
- **考察点**：time.Timer vs time.Ticker 的选择（一次性/周期）；Ticker 的 Stop 与 drain channel 手法（Go 1.23 前 stop 后取值的坑）；每个任务独立 goroutine 的生命周期管理。
- **常见错误**：任务执行时长 > 间隔导致 Ticker 溢出堆积；Stop 后 channel 残留导致 select 误触发；调度器回收与任务的竞态。
- **验证**：时间戳日志显示间隔稳定；停止后不再触发且无泄漏；-race 干净。

## 题 10：select 随机性陷阱题

- **题目**：两个 case 同时就绪时 select 随机挑一个执行——写演示程序并解释现象；推导「多个就绪 case 时公平性」；再答追问：如果两个 case 都有缓冲且一直就绪，会发生什么（饿死某侧吗）。
- **考察点**：select 的就绪判定与随机选择语义；随机性来自 Go runtime 的伪随机轮询；对「循环 select 双就绪」的直观理解（不会死锁，交替被选，公平但不保证轮询）。
- **常见错误**：以为按 case 顺序或按就绪顺序执行；写「确定性交替打印」用 select 双就绪（结果随机，应当用题 2 的链式方案）；default 分支导致的忙轮询（busy loop）。
- **验证**：多次运行统计两侧执行次数大致均匀；能写成「select 双就绪演示 + 结论」的产出型笔记。

## 题 11：channel 关闭广播

- **题目**：1 个发令 goroutine、N 个等待 goroutine：发令后所有等待者同时恢复执行（广播/close 即一发多收）；再设计一个「单发单收」对照解释区别。
- **考察点**：close(ch) 的广播语义（所有接收方同时收到零值）；「关闭即信号」惯用法（sync 里的 event channel）；与 context cancel 的等价/演进关系。
- **常见错误**：发令后 close 与接收方个数不匹配；误以为 close 只能由一个接收方消费（那是非广播 channel 的错觉）；关闭后再发数据（panic）。
- **验证**：N=1000 并发等待全部同时 10ms 内恢复；只关闭一次。

## 题 12：信号量实现

- **题目**：用 channel 实现计数信号量：Acquire（取 1 个空位）、Release（还 1 个）；并实现「有界」版本——最多同时 n 个 goroutine 进入临界区。
- **考察点**：缓冲 channel「满=被占用、空=全空」的信号量语义；Acquire/Release 配对防泄漏；defer 释放的时机。
- **常见错误**：Release 多于 Acquire（信号量膨胀）；获取后 defer 顺序反了（先释放别的）；用 WaitGroup 代替信号量（语义不同：信号量是资源计数）。
- **验证**：压测并发进临界区数量峰值 == n；-race 干净。

## 题 13：并发控制同时最多 N

- **题目**：一批 URL 下载任务（可用 sleep 模拟），控制同时进行的任务数最多 N（如 N=5）+ 总超时——P1 扫块批量 RPC 调用的并发控制原型。
- **考察点**：题 12 信号量与 errgroup 用法的选型（Golang.org/x/sync/errgroup 的 SetLimit）；早期取消（一个失败全部停）与「继续跑完」两种策略；结果收集的并发安全。
- **常见错误**：不设限把 RPC 打爆（这就是限流题的现实动机）；errgroup 内 task 返回错误后继续派发、恐慌在 goroutine 里吞掉；收集结果的 slice 并发写（-race 必报）。
- **验证**：同时运行峰值 == N（日志时间戳验证）；失败传播正确；-race 干净。

## 题 14：Unbuffered channel 死锁诊断

- **题目**：给定 3 个「会死锁」的代码片段（只收不发 / 只发不收 / 循环等待两手各持 channel），要求：指出死锁点、说出哪一行卡住、修复它。
- **考察点**：无缓冲 channel 同步握手的本质（发送方阻塞直到有人接收）；死锁三要素的 Go 表现；`go vet` 与运行 panic「all goroutines are asleep - deadlock!」的诊断用法。
- **常见错误**：把死锁当「慢」排查半天；在 defer 里发送（defer 晚于必要）；忘记 main 也是 goroutine 也要参与配对。
- **验证**：能逐题写出「卡在哪一行、为什么」的文档（产出型笔记题目），修复后跑通。

## 题 15：数据竞争修复练习

- **题目**：给一段含数据竞争的程序（如多 goroutine ++ 共享计数器、或"并发读+写 slice"），要：先用 `go test -race` 证实、解释竞态为什么可能「跑起来没事」、再用三种方案各修一遍（mutex / channel 式原子化 / sync/atomic）。
- **考察点**：数据竞争的定义与 Go 内存模型的现实意义（`go.dev/ref/mem` 选读）；-race 检测原理一句话（读写序检查 + 影子内存）；atomic 的适用边界（单值计数）与「原子 ≠ 事务」辨析。
- **常见错误**：修完不看 -race（改了个寂寞）；用「先加锁再 -race」掩盖而非定位根因；把复杂状态用 atomic 拼出中间态（应该整体加锁）。
- **验证**：`go test -race -count=100` 全绿；文档记录三种方案的性能对比（可提 benchmark）。
