# standards/project-acceptance-10.md — 完整项目 10 条验收标准（v1.0）

> 适用范围：P0 短链服务 / P1 链上充值监控 / P2 迷你交易所（旗舰）/ P3 DEX Clone / P4 Solana 小项目。
> 通过条件：**10 条全部为「是」**（P4 的达标线见其 SPEC）；任一为「否」= 项目未通过，补齐证据后再验。
> 每条给出：定义 → 可勾选判据（外部可验证）→ 对例 / 错例。判据中的工具名（go、forge、Slither 等）按项目类型取用。
> 验收结论与修订记录写入 `QA/review-log.md`，证据一律留痕在项目 README 或 docs/ 下。

---

## ① 测试完备（覆盖率 ≥ 80% + fuzz/边界用例）

**定义**：核心逻辑有自动化测试（非手工验证），覆盖正常路径、边界与异常路径；纯逻辑模块（撮合、账务、状态机、合约数学）有 fuzz 或等价性质测试。

**判据**（全部为是）：
- [ ] `go test -cover ./...`（合约项目用 `forge coverage`）输出全仓覆盖率 ≥ 80%，且命令输出与截图存入项目 README「测试」节
- [ ] 关键包覆盖率 ≥ 90%，报告中能看到包名与数字（关键包由 SPEC 指定：P2 至少含撮合、账务、状态机）
- [ ] 至少 1 个 fuzz 测试函数（Go：`FuzzXxx`；Foundry：`testFuzz_` 或 invariant），CI 或本地运行 ≥ 1000 轮无 panic/failure 记录在案（记录包含轮数数字）
- [ ] 边界用例清单每项对应一条命名测试：空输入 / 零金额 / 重复幂等键 / 并发同价下单 / 精度小数位 / 资金不足 / 重复提交
- [ ] 单测不依赖网络与真实外部服务（外部依赖用 mock/stub 或 docker-compose 起的真服务）

**对例** ✅「`go test -cover ./...` 输出 84%（撮合包 93%），截图与命令原文存 README；`FuzzMatchInvariant` 跑 2000 轮 0 失败，记录见 docs/test.md」
**错例** ❌「测试写得比较全」「所有核心函数都测了」「测试都在本地，我删掉了跑结果」

## ② 真实部署（testnet + 源码验证）

**定义**：项目不止在本机跑通——服务有公网可达地址，合约在公开网络的区块浏览器完成源码验证。

**判据**：
- [ ] Go 服务项目：提供公网可访问的 URL（VPS 或隧道），README「部署」节记录 URL 与部署日期，验收当天可访问
- [ ] 合约项目：部署地址存在（Sepolia/Solana devnet），地址写进 README
- [ ] 合约在 Etherscan（Sepolia）/ Solscan 完成源码验证，页面显示 Verified 标志，验证截图存 README
- [ ] 部署过程可重复：部署脚本或命令记录在 docs/deploy.md，含环境变量清单（不含真实密钥）

**对例** ✅「Pair 合约 0x1a2b… 在 Sepolia Etherscan 显示 Contract Verified ✓，截图见 README；部署脚本 deploy.sh + .env.example 见 docs/deploy.md」
**错例** ❌「我在本机跑通了」「部署了但没验证，浏览器报 Not Verified」「地址在终端滚动里找不到了」

## ③ 安全自查（威胁模型 + 工具扫描）

**定义**：对项目做系统的安全自查——合约项目跑静态分析工具，服务端项目写威胁模型，二者都覆盖资金/权限相关的高危路径。

**判据**：
- [ ] 合约项目：提交 Slither 运行报告（命令 + 输出文件存 docs/security/），标题 severity 为 medium 及以上 0 条；若有，每条附「已修复」或「已评估可接受 + 理由」
- [ ] 服务端项目：docs/security.md 威胁模型，覆盖 ≥ 4 项资产 × 对应攻击面 × 缓解措施（资产例：用户余额、提现签名、充值入账、行情数据）
- [ ] 资金相关必查项每项有测试或书面说明：幂等键防重放（同一 tx 重复投递）、金额精度（浮点/小数位处理）、越权（访问他人资产/无签名提现）
- [ ] 提现/签名类功能（P2）：私钥与助记词不进代码库、不进日志，密钥管理方式有书面记录

**对例** ✅「Slither 输出 0 high / 1 low（reentrancy-eth：已评估为 CEI 模式下的误报，报告存 docs/security/slither-medium.md）；威胁模型覆盖充值入账、余额、提现、密钥 4 项资产」
**错例** ❌「项目应该挺安全的」「Slither 跑过有 3 个 high 但没处理」「密钥写在配置里提交了」

## ④ 文档齐备（架构图 Mermaid + ADR）

**定义**：README 与 docs/ 可让陌生人（含 2 个月后的你和面试官）不提问就理解项目。

**判据**：
- [ ] README 含 Mermaid 架构图（或同等可渲染图），至少 4 个组件方框 + 数据流方向标注（如 P2：网关→订单服务→Kafka→撮合→账务→WS）
- [ ] docs/adr/ 至少 3 篇 ADR，每篇含背景/备选方案/决定/后果四要素，至少 1 篇是「中途换方案」的记录
- [ ] README 齐全四节：快速开始（带编号步骤）/ 架构 / 验收勾选（本文件对照表）/ 演示链接
- [ ] 文档术语与课程术语表一致（撮合/matching engine、账务/ledger 等，见 CLAUDE.md 第 1 节）

**对例** ✅「ADR-003：将扫块从纯轮询改为 WS+轮询双轨，记录了动机（延迟）、备选（仅 WS）与后果（需处理断供）」
**错例** ❌「README 写了 200 行但没有架构图」「ADR 只有『决定用 Kafka』一句话」

## ⑤ 可演示（3-10 分钟录屏）

**定义**：有一条独立于讲解者的演示证据——录屏，评审与面试官可自行观看。

**判据**：
- [ ] 录屏时长 3-10 分钟，文件存项目 demo/ 目录，README「演示」节有链接（本地路径或公网）
- [ ] 录屏包含三幕：启动/部署 → 一条完整业务链 → 关键数据/界面变化特写（含讲解或字幕）
- [ ] 录屏配套 demo/script.md 分镜脚本（每幕：操作/预期画面/讲解要点），评审可对照

**对例** ✅「6 分钟录屏：启动服务 → 充值测试币入账 → 下单 → 撮合成交 → WS 收到 ticker → 账户三栏变化，全程中文讲解，见 demo/demo-p2.mp4」
**错例** ❌「随时可以演示给你看」（未留存任何可复核文件）「录了个 20 秒黑屏只有结尾」

## ⑥ 完整闭环（UI 或 CLI 走通全业务流）

**定义**：存在一条从用户入口发起、结束于用户可感知结果的主流程，且该流程有证据（录屏或脚本输出）。

**判据**：
- [ ] 主流程至少一条，对应各项目验收线：P0 创建短链→访问跳转→统计页数字变化；P1 充值→监控服务入账→面板/WS 帧可见；P2 注册→充值→下单→成交→提现回执；P3 真实 swap 后余额变化 + tx 上链；P4 模板程序交互成功
- [ ] 主流程证据可复核：录屏（见⑤）或自动化脚本输出（日志/HTTP 响应/cURL 序列）
- [ ] 异常路径 ≥ 1 条有证据：资金不足下单被拒 / 重复提交被幂等拦截 / 余额不足提现被拒

**对例** ✅「cURL 序列完整记录：POST /order（余额不足 400）→ 充值 → POST /order 200 → GET /trades 返回成交 → WS 收到 trade 帧，输出存 demo/closed-loop.txt」
**错例** ❌「CLI 能跑，但删除数据库重来就说不清用户入口是哪条」「只演示了 GET /health」

## ⑦ 可复现（依赖锁死 + 一键重跑）

**定义**：陌生人（或三个月后的你）在干净环境按 README 能重建项目，不靠记忆与手工补位。

**判据**：
- [ ] 依赖锁定文件已提交：Go 项目 go.mod/go.sum；前端 package-lock.json；合约项目固定 Solidity 与 Foundry 版本（foundry.toml + CI 中的 pinned 版本）
- [ ] 一条命令起全环境：`docker compose up -d`（或等价脚本），配套 .env.example（占位符，不含真实密钥）
- [ ] 全新环境按 README 编号步骤 ≤ 30 分钟跑通；README 步骤与脚本一一对应，无「然后手动改了配置」类缺步
- [ ] 数据初始化（migration/seed）可重复执行或文档写明清库方式

**对例** ✅「git clone → cp .env.example .env → docker compose up -d → make migrate → make run，27 分钟在全新 M 系 Mac 跑通（记录见 README）」
**错例** ❌「依赖装没装看我本地；步骤 4 忘了写，那个端口只能我机器开」

## ⑧ CI 自动化

**定义**：GitHub Actions 流水线在每次 push 自动执行质量门禁，结果留痕。

**判据**：
- [ ] 流水线包含四步：lint + test + coverage + build（合约项目：forge fmt --check + build + test + coverage），push 即触发
- [ ] 覆盖率门禁在 CI 内强制（低于 80% 流水线红，与判据①数字一致）
- [ ] 最近 10 次 push 全绿；绿标截图存项目 README「CI」节（允许含 1 次「失败→修复→绿」的完整记录）
- [ ] CI 使用固定工具版本（如 actions/setup-go with go-version 与 go.mod 一致）并有依赖缓存

**对例** ✅「workflow 见 .github/workflows/ci.yml；最近 10 次全绿截图存 README；一次 golangci-lint 失败后 1 小时内修复的记录在 review-log」
**错例** ❌「CI 是绿的，但执行时间在 3 个月前的唯一一次」「没有 coverage gate，测试直接跳过」

## ⑨ 复盘文档（踩坑 + 取舍）

**定义**：项目结束后有一份直面问题的复盘，是面试「项目深挖」的台词库。

**判据**：
- [ ] docs/review.md（或 REVIEW.md）至少 3 个坑，每个含四要素：现象 / 根因 / 解法 / 耗时
- [ ] 至少 2 个取舍决策，每个含：选项对比表（≥2 个选项 + 各自代价） + 选择理由 + 如果重来会怎样
- [ ] 每个坑与取舍可改写成 2 分钟面试故事（开头-问题-排查-解决-结果，结构完整）
- [ ] 复盘写明了坑发生的阶段与日期，与日志/commit 可交叉验证

**对例** ✅「坑#2：消费组重平衡导致重复入账（现象），commit 在消费成功后、未提交 offset 时发生重平衡（根因 20%），改为幂等键+唯一约束兜底（解法 1d）。面试讲法：……」
**错例** ❌「整体还算顺利，遇到点小问题都解决了」「记不清了，就是当时调了很久」

## ⑩ 结果留痕（报告/地址/CI 绿标截图）

**定义**：项目所有关键结果汇总到一处可导航的成果页，链接全部有效。

**判据**：
- [ ] 项目根文档（README 或 docs/result.md）含「成果清单」节：部署地址表（合约地址/服务 URL）、测试数字（覆盖率）、CI 绿标截图、演示录屏链接、压测数字（若适用）
- [ ] P2 压测报告含具体数字：并发数 / QPS / P50 / P99 / 错误率，且来自 k6 输出（非手写）
- [ ] 清单中每个链接/路径验收当天可打开（录屏文件、截图、命令输出文件均存在）
- [ ] 本 10 条验收表本身勾选留痕（项目 README 复制勾选版或 QA/review-log.md 记录）

**对例** ✅「成果清单：合约 0x…（Verified）、API https://…、coverage 84%（截图）、demo-p2.mp4、k6 报告 P50=4ms P99=31ms @1000 并发 0 错误，全链可点」
**错例** ❌「结果都在我本地」「压测数字凭印象写了个 5 万 QPS，没有报告文件」

## 验收流程（每个项目结束执行）

1. 对照以上 10 条逐条自测，用「判据」列的勾选框逐项勾选。
2. 缺证据的条：补齐证据（截图/输出文件/录屏），证据位置写进 README。
3. 未达标条目列入「修复清单」，修复后重测该条。
4. 全部为「是」后，把结论（含每条的证据链接）写入 `QA/review-log.md`。
5. 项目 README 的「验收」节内嵌本表勾选版，作为可被面试官核验的留痕。
